# 工具调用、回执与恢复契约

阶段 A 和 B 设计稿，更新于 2026-11-27。场景是远程工具已把文件保存到可保留的工作区，回执在返回途中丢失。阶段 A 用进程内工具完成写入，再由测试传输替身注入丢失回执。工作区保留、恢复和清理遵循环境配置。 [Tool.Invoke 的请求与回执](tool-invoke.md)

## 四个组件的职责

| 组件 | 负责的动作和证据 |
| --- | --- |
| **运行器** | 用本次 Run 的授权快照校验拟调用及预算。派发并关联 `RunID`、`CallID`，接收回执，裁决本轮和 Run 的状态。B 通过检查点保存派发和恢复所需的状态 |
| **Mesh** | 按当前绑定传输请求、回执、取消和状态查询。保持调用方身份、`RunID`、`CallID`、截止时间和绑定信息。传输状态记录送达证据，工具执行状态由工具提供方和执行环境确认 |
| **工具提供方** | 核验来访身份、工具授权和资源范围，把调用翻译为环境操作。控制工具输出大小，将确定的执行结果整理为回执。B 为可恢复的有副作用调用保存最小回执 |
| **执行环境** | 执行并确认工作区中的保存操作。按环境句柄控制工作区及文件访问，提供可用的写入记录、资源终止和释放状态 |

## 从授权到回执

1. 运行器接受有效的 `ModelCompleted`，检查取消和预算，校验工具、参数及授权。可关联的工具校验拒绝发布 `tool.completed(rejected)`，并保留错误供模型处理。取消或预算停止条件生效时，运行器按 Run 停止规则收尾。 [派发前的模型边界](model-adapter.md#工具派发边界)
2. 通过校验后，运行器按受理时确定的工具绑定派发，产生 `tool.dispatched`。`RunID` 和 `CallID` 在原调用、工具回执和恢复查询中保持一致。Mesh 只转发这次执行请求。
3. 工具提供方复核请求，使用运行器派发前取得的按次授权，经 Mesh 请求环境执行保存操作。执行环境确认保存结果，支持时同时提供工作区身份、目标版本及可关联的写入证据。 [权限复核与拒绝](run-authorization.md#按次授权怎么复核)
4. 工具提供方把确定的执行结果整理成回执，经 Mesh 返回。运行器校验回执与本次调用匹配，才记录该工具结果。整批工具结果齐全后可提交本轮消息并继续 Agent Loop。

| 运行器收到的证据 | 运行器如何判定 |
| --- | --- |
| 本地或传输层能确认请求未发出，或提供方确认拒绝且未执行 | 明确未执行，可以返回可关联的错误 |
| 只有传输或接收确认 | 可以追踪调用，仍等待执行回执 |
| 匹配原调用的可信执行回执 | 确定执行结果，按正常工具返回规则推进 |
| 请求可能已到达，随后超时、取消或断连 | 没有执行回执时按结果不明处理。读不到记录或文件也不足以判定未执行 |

## 阶段 A 收尾

阶段 A 把 Run 状态和结果暂存在运行器内存。运行器退出后由宿主决定下一步。工具写入的文件仍由工作区的保留策略管理。

1. 本场景中，运行器在派发后收到断连，无法确认文件保存结果。它停止同一 Run 的后续工具和模型调用，发布 `tool.completed(unknown)`，提交 `ToolOutcomeUnknown`，再发布 `run.finished`。`Result.Stop` 记录原调用标识和断连原因。已完成的工具批次和消息按原规则保留。
2. 运行器关闭本地调用句柄，经 Mesh 请求工具提供方取消在途工作，请求执行环境释放 Run 持有的环境资源。执行环境按原策略保留工作区或回收资源。`Wait` 可以先返回 Run 终态，资源释放仍未确认时保留独立诊断。
3. 运行器对原 `CallID` 只发起一次执行请求。终态提交后的迟到回执可用于诊断，`Wait` 继续返回已保存的终态。 [SDK 终态契约](go-sdk-contract.md#调用错误与运行终态)

## 阶段 B 恢复

### 重启和接管

建议 B 先验证同一部署内的进程重启。新进程读取检查点后取得同一 `RunID` 的推进权。多实例接管是后续部署场景。例如原运行器失联但仍在运行，新运行器取得推进权后，旧运行器又尝试提交结果。存储只接受当前所有者提交。工具提供方的有效回执仍可由新运行器核验使用。

### 保存可核对的记录

- **运行器与检查点组件** 为可恢复 Run 增量保存已完成的轮次。对存在或无法排除外部副作用的调用，在首次传输前保存派发意图。记录 `RunID`、`CallID`、`Step`、工具绑定、参数快照或引用及其摘要、授权范围、环境引用，以及续跑所需的已确认结果。仅有意图时，实际派发进度仍待核对。
- **工具提供方** 在有副作用的调用执行前登记身份和请求摘要，完成后先保存最小可查询回执，再回包。回执保留执行结局、原因码和必要的结果字段或稳定引用。相同调用身份的重复请求返回已有状态，内容不同则报冲突。调用记录绑定原 Run 的授权主体和工具绑定，换运行器后仍须验证对原 Run 的访问权。
- **只读调用** 可随本轮检查点保存续跑需要的小结果或稳定引用。中断后缺少结果时，只有工具声明可安全重读、且业务允许采用重读值时才重新读取。依赖原值的轮次须保留原值或能定位原值的版本引用。
- **执行环境** 在支持时提供调用关联的写入证据，可用于弥补文件已保存、工具回执尚未持久化的窗口。保存动作与工具回执各自持久化，恢复时可能只有其中一份记录。

检查点保存用于续跑的有界结果。产物由执行环境或产物存储持有，检查点和回执引用同一份产物。保存期覆盖恢复与去重窗口，到期后按各自的保留策略回收。

### 查原调用，按证据接续

1. 运行器取得原 Run 的所有权并读取检查点。将仍未终结的调用标记为待核对，由 Mesh 按原 `RunID`、`CallID` 查询工具提供方。旧运行器失去所有权后，其迟到响应只能进入诊断。原环境中的在途操作仍需独立核实。
2. 优先读取工具提供方的回执。回执缺失时，由工具提供方查询原工作区的写入证据。只有证据能关联原调用、目标和写入内容，且足以重建原工具结果时，才补出回执。文件路径存在或内容摘要吻合只能描述查询时的状态。
3. 按恢复证据决定后续动作，原 Run 的取消、截止时间和预算继续生效。待核对期间可释放临时调用资源，按恢复窗口保留工作区引用和证据。需要工作区的后续步骤先确认环境可用。运行器确认落定后只提交一次本轮结果。

| 查证结论 | 处理方式 |
| --- | --- |
| 已有匹配回执，或能从关联证据重建回执 | 接回原结果。Run 仍可继续时，在收齐本轮工具结果后从检查点推进 |
| 已确认未执行，且原尝试已不能再产生效果 | 把明确失败交回模型，或按已生效的停止原因收尾。后续若提出新调用，仍按授权和预算重新检查 |
| 缺少证据、原操作仍在途或原工作区不可查 | 保持待核对，仅查询状态。达到核对窗口或运行期限，或收到停止请求时，以 `ToolOutcomeUnknown` 结束并按阶段 A 的规则清理 |

待核对期间暂停新的调用，`Wait` 仍等待终态。阶段 A 已提交终态的 Run 保留原结果。阶段 B 从尚未终结且有检查点的 Run 接续。核对期限、状态查询接口和待核对的 SDK 事件后续评审。

## 大输出与结果大小

大输出由工具提供方或执行环境边读边写到产物。运行器接收有界的工具结果，内容可以是小正文，或限长摘要加产物引用。阶段 B 保存续跑所需的小结果及引用。完整文件的引用携带稳定版本、字节数和内容哈希。引用、摘要和回执字段一并计入结果大小。

| 上限 | 谁执行 | 如何验收 |
| --- | --- | --- |
| 单个数据块及缓冲大小 | 工具提供方分块写入，接收端校验块大小并限制缓冲 | 单块超限时拒绝它。连续输出时内存占用受缓冲配置约束 |
| 单次原始输出字节和截止时间 | 工具提供方或环境按受管输出累计，命令的 stdout 和 stderr 共用限额。运行器维护截止时间，环境另行约束单次调用及整个 Run 的产物存储额度 | 正好达到上限仍可完成。超限或到期时停止收集并请求停止工作，按限额收尾 |
| 最终工具结果大小 | 提供方在返回前测量完整编码大小，运行器接收时复核 | 允许范围内的小结果、摘要和引用可进入模型上下文。上限内留出空间表达超限等结局 |

收齐字节后，还须确认工具执行结束并校验产物尺寸与哈希，才发布完整产物引用。断流或超限产生的部分数据按环境策略清理或留作诊断。已经确认的工具效果仍记入回执，效果不明时沿用 `ToolOutcomeUnknown`。 [预算分配与超限收尾](run-budget.md)

## 文件搜索的资源边界

GNU `grep -m` 按匹配行数停止读取，GNU grep 的输入行长则受可用内存约束。搜索范围很大、匹配很少或只有一条巨长的行时，需要另外限制读取、缓冲和执行内存。 [GNU Grep 手册](https://www.gnu.org/s/grep/manual/grep.pdf)

阶段 A 建议优先给模型提供有界的文本搜索工具。它接收匹配条件和搜索范围。运行器按宿主配置、Run 剩余额度和请求范围下发有效限制。工具提供方执行读取限制，执行环境负责隔离和内存限制，Mesh 保留限制与终止原因。

| 边界 | 约定 |
| --- | --- |
| 输入范围 | 限制遍历项数、候选文件数、单文件可读量、累计扫描字节和截止时间。文件大小用于提前筛选，读取时按实际字节计量，覆盖文件持续增长和零命中的情况。跳过文件或缩短扫描范围时记录原因 |
| 匹配缓冲 | 起步采用普通文件的按行文本搜索，限定查询大小和单行缓冲。分块读取，搜索单元超限时停止该文件的扫描并标记覆盖不完整。确定匹配所需的行必须读完整 |
| 执行内存 | 环境在启动通用命令前为整个进程树建立内存限制，并给运行器保留容量，按总预算接纳并发工作。限额触发后终止并回收对应工作负载。受控的进程内搜索工具须通过有界缓冲和并发验收 |
| 返回结果 | 设整个请求的命中数、每条预览和最终编码大小上限。命令输出及错误输出的收集都受缓冲和总量约束。结果附扫描量、覆盖状态和停止原因。空结果只有在指定范围完整扫描后才表示零命中 |

扫描、匹配或内存限额触发时，已确认的命中仍可按预算返回，结果标记为部分完成或失败。执行环境能确认触发内存限制时，返回可识别的资源错误。运行器可以据此让模型在剩余额度内缩小范围。 [大文件搜索验收](run-budget.md#大文件搜索验收)

通用命令只绑定到能提供所需隔离和内存上限的环境。Linux 可参考 cgroup v2 的进程组内存控制，其他环境各自验证同等能力。 [Linux 内核文档](https://docs.kernel.org/admin-guide/cgroup-v2.html#memory)

## 验收场景

| 故障注入 | 阶段 A | 阶段 B |
| --- | --- | --- |
| 保存后丢掉回执 | 文件确实保存一次。`Wait` 返回 `ToolOutcomeUnknown`，后续工具未执行 | 查到原回执后接续原 Run，保存操作仍只执行一次 |
| 文件保存后、工具持久化回执前崩溃 | 结果不明，发起资源清理 | 有原调用写入证据时补回执。仅有文件存在或摘要时保持待核对 |
| 查不到回执，原尝试稍后才完成 | 已发布终态保持固定 | 保持待核对，收到有效回执才推进。核对期间写入执行次数不增加 |
| 同机重启后读取检查点 | 原进程的内存状态失效 | 新进程按原 `CallID` 查询，使用已确认结果续跑 |
| 多实例场景下，旧运行器在失去推进权后再次提交 | Run 绑定原受理进程 | 仅当前所有者可提交。工具提供方的同一有效回执只进入模型上下文一次 |
| 大输出连续产生或写到一半断流 | 结果和缓冲有界。部分产物只作诊断 | 续跑使用限长结果和稳定引用，按同一份产物核对，不重复写入原始输出 |
| 搜索大文件一直无命中，或文件持续增长 | 按配置上限停止读取并报告已扫描字节。扫描不完整时返回对应状态 | 沿用同一搜索预算和覆盖语义 |
| 搜索遇到巨长的单行，或普通短行大量命中 | 单行缓冲和最终结果分别受限。增加输入和命中量时，验证缓冲内存保持在配置范围内 | 沿用同一有界结果 |
| 通用命令或其子进程把环境内存用到限额 | 环境报告限额命中并回收工作负载。验收同时记录工具及运行器的峰值内存，确认另一路 Run 可继续 | 沿用同一隔离与收尾规则 |

派发意图、执行结果和迟到写入的处理，可参考 [Temporal 团队的 Pi 恢复实验](https://temporal.io/blog/the-immortal-life-of-pi-running-the-pi-coding-agent-on-temporal#unknown-outcomes)。
