# SuperAgent 总体架构

状态为设计草案，更新于 2026-11-27。组件和部署关系见 [架构图解](../humanized/architecture.md)。

## 已确认的方向

- 使用 Go，从空仓库开始设计。`agentic-go` 的代码、已有接口和接入兼容性都在本项目设计边界之外。
- 最终交付独立 TUI 和可嵌入的 Go SDK。两者共用执行契约。不同对话能并发执行，各自流式回复和取消。
- 各组件按接口独立抽象，跨组件调用统一经过 Mesh，支持本地和远程绑定。执行环境可以放在本机、隔离沙箱或远程节点，也可以在远程节点上使用沙箱。
- 按 A、B、C 的顺序设计单次执行、可恢复执行、会话与调度。阶段 A 优先做 bypass，接管与人机协作随后逐步设计。

讨论记录见 [拉取远端最新变更](codex://threads/01a21c31-8067-7a30-8a30-390dfd1d410a)。以下职责划分和具体行为均为待审提案。

## 逻辑架构

Mesh 是统一的组件调用层。组件发布能力契约及其实现，调用方只依赖契约。每个组件都独立接入 Mesh，能够绑定进程内实现或远程端点。调用通过 Mesh 返回结果或事件。

| 组件 | 拥有的职责 | 可替换实现示例 |
| --- | --- | --- |
| 运行器 | 推进单次 Run 的模型与工具循环，裁决预算、取消和最终结果 | 嵌入式 Go 运行器或远程运行服务。每个 Run 由一个运行器实例推进 |
| 模型适配器 | 由模型工厂创建或取得 API 客户端，调用模型并转换文本流、完成原因和结构化工具调用 | 本地 SDK 适配器或远程模型服务适配器。适配器位置和模型服务位置可以不同 |
| 工具提供方 | 声明参数和调用契约，执行工具并落实其业务授权。需要工作区的操作使用获授的环境句柄 | 进程内 Go 工具、远程业务工具或在指定执行环境中运行的工具 |
| 执行环境 | 分配和释放执行资源，控制工作区、文件、进程、网络及配额。按能力报告支持的隔离与取消方式 | 本机环境、隔离沙箱、远程工作节点。远程节点可进一步为工作负载分配沙箱 |
| 运行事件 | 按 Run 接收和提供实时进度，管理订阅与背压。运行器发出事件并拥有终态 | 本地有界流或远程事件流。观察中断时仍可以向运行器查询最终结果 |
| 检查点与恢复 | 保存可恢复的执行边界，处理所有权和工具回执 | 本地持久化实现或远程状态服务，待 B 明确一致性要求 |
| 会话与调度 | 读写会话历史、提供历史快照，处理提交顺序、容量与调度 | 宿主自有实现、本机会话组件或远程会话服务，待 C 定义契约 |

## 职责归属

建议一次 Run 的推进权和状态归同一个运行器。预算检查、权限门禁、消息组装和工具派发是运行器内可分别设计的职责。阶段 A 先在运行器内组合这些职责，模型、工具、事件和环境通过 Mesh 独立绑定进程内实现。

| 职责 | 谁负责 | 如何配合 |
| --- | --- | --- |
| Loop 内的观察 | 运行器收集和校验模型回复与工具回执，决定下一步 | 适配器和工具提供方经 Mesh 返回各自的结果。完整的工具批次才能进入下一轮模型输入 |
| 宿主观察进度 | 运行器生成语义事件并分配顺序。事件组件负责订阅、缓冲和断连 | 宿主或 TUI 通过 `Observe` 控制观察的起止，关闭观察时 Run 继续。改变 Run 状态的指令经 SDK 发给运行器 |
| 控制预算 | 运行器维护 Run 额度，并在每次模型请求和工具派发前按余额裁决 | 宿主配置额度，模型适配器和工具在数据源执行字节限制，环境组件执行资源限制和本地接纳。跨 Run 调度归 C。 [预算契约](run-budget.md) |
| 权限门禁 | 宿主授予本次 Run 的工具能力，运行器按授权快照生成可见清单，并在派发前检查授权和参数 | 工具提供方复核调用身份、获授能力和业务权限。环境组件落实资源隔离。bypass 使用预授权作为执行依据 |
| 发出工具指令 | 运行器在接受完整模型回复后统一派发，并关联 `RunID` 与 `CallID` | Mesh 按绑定寻址和传输调用，工具提供方执行并返回结果。运行器据结果决定继续或结束 |
| 封装 AI API 工厂 | 模型模块内的工厂在装配时创建供应商客户端，同一连接配置下的模型绑定共用客户端 | 运行器使用受理时确定的 `ModelRef` 调用适配器。适配器侧持有客户端及凭据，并负责请求和响应转换。 [模型工厂契约](model-factory.md) |
| 管理 Run 上下文 | 运行器持有本次执行的历史快照与已提交轮次，并组装每次模型请求 | 模型适配器将规范消息转换为供应商协议。检查点组件在 B 保存恢复同一 Run 所需的状态 |
| 会话历史读写 | 阶段 A 由宿主负责。阶段 C 由会话模块通过存储接口读取快照和提交历史 | 运行器交回 `Result.Messages`。会话模块决定提交时机及并发处理，建议以历史版本检查冲突、以 `RunID` 去重 |

## 消息构造与历史提交

1. **宿主或 TUI** 把用户输入构造成 `UserMessage`。阶段 A 的宿主选择历史窗口并提供快照，接入 C 后由会话模块按策略选择。
2. **运行器** 用历史快照、本次用户消息和当前 Run 已完成的轮次组装 `ModelRequest.Messages`，指令单独放入 `Instruction`。运行器将完整模型回复和工具返回值整理成标准消息，有工具调用时，等结果成批齐全后再将本轮纳入下一次模型上下文。
3. **模型适配器** 把规范消息编码成供应商 API 格式，保留工具声明和对应结果的关联。 [模型请求契约](model-adapter.md#请求)
4. **宿主或会话模块** 按策略提交 `Result.Messages`。增量包含本次用户输入和已提交轮次。B 的检查点负责恢复执行，C 的会话历史负责后续对话。 [阶段 A 消息组装与返回契约](message-assembly.md)

## Mesh 调用契约

- **组件绑定。** 阶段 A 由宿主按组件选择进程内实现，后续可接入远程传输。运行器在受理时固定本次使用的绑定与工具授权，TUI 通过同一个 SDK 接入。 [宿主装配与 Mesh 绑定](go-sdk-assembly.md)
- **请求与流。** 调用传递类型化消息，保留运行 ID、调用 ID、调用方身份和截止时间，以及事件的归属与顺序。接收方校验调用权限。 [Mesh 传输与配置](mesh-transport.md)
- **状态所有权。** 运行器裁决 Run 状态，事件组件提供观察，检查点组件保存恢复所需的状态，会话组件管理消息历史。Mesh 负责寻址、分派与传输，组件间的调用和事件发布通过这一层完成。
- **故障语义。** 建议区分调用明确未派发、明确结束和结果不明。跨边界派发后掉线时，按结果不明处理，除非收到可核对的结果。观察流掉线只影响观察。显式取消发给拥有 Run 的运行器，由其传递到在途工作。

## 执行环境与部署

运行器和执行环境可以分别部署。需要工作区的 Run 绑定一个受限环境句柄，工具按次获得访问授权。需要隔离的操作绑定到符合要求的环境，环境不可用时返回明确错误。 [执行环境契约](execution-environment.md)

| 示例部署 | 运行器与模型 | 工具和执行环境 |
| --- | --- | --- |
| 全本地接入 | 运行器和模型适配器嵌入 TUI 或宿主 | 工具在宿主进程内接入，使用本机环境绑定 |
| 本地编排、沙箱执行 | 运行器仍在宿主进程，模型适配器可本地或远程 | 工具通过 Mesh 使用本机沙箱中的工作区与执行资源 |
| 远程执行 | 运行器可以留在本地，也可以部署到远程 | 执行环境绑定到远程工作节点，按需在节点内使用沙箱 |

阶段 A 用显式配置验证进程内绑定。具体沙箱机制、文件传输和远程协议另行评审。

## A、B、C 的交付边界

| 阶段 | 本阶段解决的问题 | 本阶段的验收 |
| --- | --- | --- |
| A · 单次执行 | 在 Mesh 契约上完成 bypass 循环。每个运行有独立状态、事件、预算和取消范围 | 一个 Go 宿主能观察两路独立运行。验证进程内分派，通过故障注入验证断流与回执丢失。详见 [阶段 A 设计](stage-a-bypass.md) |
| B · 可恢复执行 | 定义检查点、恢复可见的状态和运行所有权。明确中断时已派发工具的结果如何查询与确认 | 执行进程重启后能从已提交的边界继续。对结果不明的外部操作，优先查回执或等待明确处理，避免重复执行 |
| C · 会话与调度 | 读写历史、提供历史快照，为会话管理提交顺序和资源容量。为 TUI 提供会话维度的运行管理 | 两个会话各自推进、流式显示和取消。退出重进后的历史与运行恢复由已确认的 B、C 契约决定 |

TUI 可以在 A 的契约稳定后先验证双路并发和取消。产品首发需要真实模型接入和可独立启动的终端入口。首发是否同时交付 B、C 的完整能力单独决定。暂停续跑、逐步接管、人工审批、运行中插话和多 Agent 协作分别评审。

## 并发边界

- **Run 是一次执行。** 从一份固定输入出发，经历一轮或多轮模型与工具交互。每个 Run 只由一个执行流程推进。独立 Run 的等待、事件消费、预算与取消相互隔离。
- **Session 是一条持续对话。** 后续由 C 管理消息和历史提交。建议同一会话先只允许一个活跃 Run。忙时明确告知调用方，TUI 保留本次输入。自动排队、打断续跑或同历史分叉，需要先确定输入可见性和提交顺序。
- **耗时资源单独限流。** 并发验证以仍有可用容量且依赖支持并发为前提。在 A 由宿主配置模型、工具和执行环境的限流。C 再决定如何跨运行器分配容量、排队与保证公平性。

产品验收用两个独立会话。会话甲卡在慢工具时，切到乙并发送消息。乙在甲尚未结束时开始流式输出。取消甲之后，乙继续输出，两个会话的文本和工具结果各自归属正确。

## 调研依据

- **Pi** 展示了流式模型回复、工具执行、再次请求模型的基本循环，也让终端、SDK 等入口复用 Agent 和会话机制。SuperAgent 借鉴循环和入口复用，先以最小 Run 契约验证。 [Pi 工作原理](https://docs.pi.dev/latest/how-pi-works)
- **OpenCode** 的会话规范区分持久事件和实时增量，并明确崩溃后可能无法判定外部工具是否已产生效果。SuperAgent 因此将检查点和中断恢复放到 B，同时在 A 区分实时输出、最终结果和状态不明的工具调用。 [OpenCode 会话规范](https://github.com/anomalyco/opencode/blob/2b8f912c8623a79688e236aa94d1e384fac3a325/specs/v2/session.md)
- **Go `context.Context`** 可把截止时间和取消传递到模型请求与工具调用。建议运行器为每个 Run 建立独立的取消范围，SDK 调用的 context 约束各自的操作。 [Go context](https://pkg.go.dev/context#pkg-overview) · [Go SDK 生命周期提案](go-sdk-contract.md#启动与生命周期)
- **Bubble Tea** 可作为 TUI 候选，框架的输入处理和渲染都属于终端入口。是否采用及其版本放到 TUI 设计时决定。 [Bubble Tea 官方仓库](https://github.com/charmbracelet/bubbletea)

## 首轮评审顺序

1. 审阅 [A 的推进权与 bypass 授权边界](stage-a-bypass.md#待确认的取舍)。它们决定一次运行在什么条件下能直接执行工具。
2. 审阅 SDK 启动、观察、等待、取消和 Mesh 故障语义。函数签名随契约一起评审，模型供应商随后确定。 [Go SDK 契约与行为接口](go-sdk-contract.md)
3. 分别讨论 B 的持久化与恢复、C 的同会话提交策略。首个 TUI 版本的交付范围等这些边界明确后决定。
