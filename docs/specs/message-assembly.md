# 阶段 A · 上下文与消息组装

宿主管理会话历史并选取输入快照。运行器持有本次 Run 的上下文，按轮组装模型请求。模型适配器负责供应商格式转换。Run 结束时，宿主从 `Wait` 取得可追加的消息增量。 [SDK 事件与结果](go-sdk-contract.md#事件和结果)

## 规范消息

```go
type Message struct {
    User      *UserMessage
    Assistant *AssistantMessage
    Tool      *ToolMessage
}

type UserMessage struct {
    Text string
}

type AssistantMessage struct {
    Text      string
    ToolCalls []ModelToolCall
}

type ToolMessage struct {
    CallID    CallID
    Content   string
    Artifacts []ArtifactRef
    Error     *ToolReason
}
```

- `Message` 三个字段恰有一个存在。阶段 A 使用文本、结构化工具调用和有界工具结果。宿主指令走独立的 `Instruction` 字段。
- 工具轮次由一条含有 `ToolCalls` 的助手消息和紧随其后的工具结果组成。每个 `CallID` 对应一条结果，顺序与声明一致。`Error` 为空表示成功，有值时存放可披露的有界错误。产物使用获准披露的引用，按原授权规则读取。 [工具回执](tool-invoke.md#toolresult)

## 宿主如何传历史

| 输入 | 契约 |
| --- | --- |
| `StartRequest.History` | 宿主从会话历史选取本次输入之前的消息，按原顺序传入。新会话可传空历史。裁剪按完整消息和工具轮次进行 |
| `StartRequest.Input` | 宿主单独传入本次用户消息，运行器追加一次。历史中的相同文本仍按原消息保留 |
| `StartRequest.Instruction` | 宿主为整个 Run 提供独立指令，运行器逐轮传递 |

受理时固定这三项的快照，包括消息里的切片和参数字节。拒绝孤立工具结果、缺失或重复配对、非法消息形状等输入错误。校验以一个历史工具轮次为配对范围，允许不同历史轮次使用相同的 `CallID`。历史中相邻的用户消息可保留，例如上一次只提交了输入。宿主后续写入历史或修改请求内的数据只影响后续请求。

## 运行器如何组装每轮

1. `ModelRequest.Instruction` 固定为宿主指令。`Messages` 依次为历史快照、本次输入、当前 Run 已提交的轮次。`Tools` 取受理时固定的授权声明。历史里的工具调用只作为模型输入，当前工具能力由本次授权决定。已交付的快照按只读使用。
2. 运行器按本轮完整请求检查输入上限和 Run 余额。阶段 A 固定历史的基线上，放不下时结束为 `BudgetExceeded`，该轮模型请求执行次数为零。历史窗口由宿主在启动前选择。 [输入计量](run-budget.md#预算与扣减) · [后续上下文压缩算法](context-compaction.md)
3. 模型适配器保留指令、消息顺序和工具配对。供应商若需要请求内唯一的工具标识，适配器对历史声明和对应结果一起映射，规范消息保持原标识。遇到无法表达的消息结构时返回明确的适配错误。 [模型请求契约](model-adapter.md#请求)

## 工具结果何时进入上下文

| 时点 | 写入规则 |
| --- | --- |
| 文本增量，或模型流未能完成 | 增量供界面预览。持有 `ModelCompleted` 并校验通过后，运行器才进入答复或工具分支 |
| 完整答复，无工具调用 | 运行器按停止顺序裁决；接受最终答复时提交助手消息和成功终态 |
| 完整回复，有工具调用 | 助手消息及结果暂存在当轮。按原顺序处理各调用，成功、明确拒绝及可回传的已知失败都可形成配对结果 |
| 工具结果齐全，提交先于停止 | 原子追加助手消息和全部配对结果。此时轮次已提交，下一次模型请求即使因预算不足无法发出，也保留这一轮 |
| 取消、超时、预算停止先于提交，或有调用结果不明 | 当轮整体留在展示及诊断路径。已确认的工具效果仍按回执报告。迟到回执可用于收尾，已停止的当轮保持未提交 |

运行器从 `ModelReply` 构造助手消息，从已校验的 `ToolResult` 或本地明确拒绝构造工具消息。工具消息只取有界正文、可披露的产物引用或错误。未处理的调用、无效回执和结果不明都无法填补配对。`message.completed` 表示收到完整模型回复，整轮提交以运行器追加消息为准。 [工具派发边界](model-adapter.md#工具派发边界) · [阶段 A 收尾](tool-call-lifecycle.md#阶段-a-收尾)

## Run 结束后交回宿主

`Wait` 返回的 `Result.Messages` 是相对 `StartRequest.History` 的追加增量。所有已受理的 Run 都交回本次用户消息一次，后接已提交的完整轮次。成功时，`Result.Answer` 是增量末尾最终助手消息的便捷视图。指令、工具定义、实时草稿、未提交轮次、诊断与原始产物留在各自的输入或结果通道。

宿主根据终态决定是否保存。宿主自行保留读取快照时的历史版本，保存时可据此校验追加位置，并按 `RunID` 幂等追加整份增量。重复调用 `Wait` 得到同一份逻辑结果。 [会话历史职责](architecture.md#消息构造与历史提交)

## 验收场景

| 场景 | 可观察结果 |
| --- | --- |
| 受理后宿主改动原消息或写入新历史 | 已启动 Run 的各轮基于原快照。本次输入在模型上下文及返回增量中各出现一次 |
| 历史孤立工具结果，或多个历史轮次复用同一 ID | 孤立结果在 `Start` 被拒。完整历史轮次按各自配对，适配器映射后保持顺序及关联 |
| 历史工具在本次 Run 无权使用，或完整模型输入超出预算 | 历史只作上下文，授权清单仍由本次 Run 决定。输入超预算时零模型派发，`Wait` 返回 `BudgetExceeded` |
| 同轮两个工具，一成功、一明确拒绝 | 下一轮看到一条助手消息和两条按序结果。拒绝随原 `CallID` 回传 |
| 同轮两次写入，一次成功、另一次效果不明 | `Wait` 返回此前已提交的增量和 `ToolOutcomeUnknown`。成功写入可从回执确认，当轮消息整体不进入历史增量 |
| 取消与最后一个结果竞争，或完整批次后下一轮预算不足 | 取消先于提交时只保留此前轮次。提交先发生时保留完整批次，即使下一轮无法派发 |
| 多个等待者拿到同一成功结果 | `Answer` 对应增量中的最终助手消息，按 `RunID` 追加一次 |
