# 最小 TUI · 双会话契约

## Purpose

让一个本地终端进程通过 SDK 操作两条独立会话，在切换视图时保留各自的草稿和流式输出，并能准确取消当前会话的排队请求或已受理 Run。

## ADDED Requirements

### Requirement: 双会话切换与输入

终端 MUST 打开宿主指定的两个本地会话，同时显示各自状态和当前会话标记。`Tab` 切换当前会话，`Enter` 提交当前会话的非空输入。终端 MUST 按会话保留草稿和对话，且每个会话同一时刻只发起一个待完成的请求。

#### Scenario: 切换保留草稿

- **WHEN** 用户在甲输入草稿，切到乙输入并发送，再切回甲
- **THEN** 乙获得自己的输入，甲仍显示原草稿及自己的历史
- **AND** 连续按下 `Enter` 只为本次意图发起一次启动，另一个会话仍可切换或发送

### Requirement: 显示排队和受理

终端 MUST 仅在收到 SDK 入队通知后显示「排队中」，取得名额后显示「受理中」，收到 Run 句柄后显示「运行中」。终端 MUST 分别呈现队列满、等待超时和受理结果待核对。

#### Scenario: 乙等待甲释放唯一名额

- **WHEN** 甲占用唯一名额，乙提交输入并进入等待，用户来回切换
- **THEN** 乙保持「排队中」，自己的 Run 流尚未开启。甲终止后，乙按原 `RunID` 自动进入受理并开始显示输出
- **AND** 队列满时直接呈现拒绝与可编辑的原输入，等待超时后恢复原输入并显示超时

### Requirement: 流式输出与终态

终端 MUST 为每个已受理 Run 建立一次独立观察，持续处理前后台事件。增量按原会话、`RunID` 和事件顺序显示。观察中断时 MUST 保持独立的 `Wait`。终态以 `Wait` 结果为准，以原 `RunID` 提交历史一次。

#### Scenario: 后台继续流式输出

- **WHEN** 甲、乙分别流式输出，用户读取甲后切到乙，再切回甲
- **THEN** 两个会话的输出分别累积，切回可见已收到的内容，切换不会重新建立 Run 观察
- **AND** 完整消息和终态替换对应预览，本次 Run 的确认增量只进入历史一次

#### Scenario: 观察中断或历史保存失败

- **WHEN** 某个 Run 的观察溢出或关闭，随后 `Wait` 返回可信终态
- **THEN** 先提示观察中断，收到终态后用完整结果收束预览，另一个会话继续更新
- **AND** 保存失败时显示待保存，原会话历史版本不变。按原 `RunID` 重试保存仍只追加一次
- **AND** 若 `Wait` 本身无法确认终态，则显示结果待核对并保留原 `RunID`

### Requirement: 取消当前会话

终端 MUST 在处理 `Esc` 时固定当前会话和本次 `RunID`。等待或受理中的请求取消启动上下文，已受理的 Run 调用 `Run.Cancel`。终端 MUST 以明确未受理的结果或 `Wait` 终态决定取消结局。

#### Scenario: 取消乙的等待

- **WHEN** 甲占用唯一名额，用户切到排队的乙并按 `Esc`
- **THEN** 乙移出队列并恢复原草稿，历史保持原版本。甲继续运行，乙的模型和工具派发为零
- **AND** 甲随后释放名额时，已取消的乙不会自动启动

#### Scenario: 取消乙的 Run 后立即切走

- **WHEN** 甲乙均已受理，用户在乙按 `Esc` 后立即切回甲
- **THEN** 取消仍发给乙的原 `RunID`，乙在收到可信终态前显示「取消中」。甲继续输出
- **AND** 终态已先于取消提交时展示原终态。空闲会话的 `Esc` 没有 Run 副作用

#### Scenario: 取消和受理同时发生

- **WHEN** 用户取消乙，乙同时取得名额并跨过受理边界
- **THEN** 确认未受理时保留草稿。若收到 Run 句柄，则继续取消同一 `RunID`
- **AND** 受理结果不明时显示「受理待核对」，沿原标识查询或向已存在的 Run 请求取消，新增启动和续跑派发均为零
