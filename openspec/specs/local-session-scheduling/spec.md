# local-session-scheduling Specification

## Purpose

让同一宿主装配内的不同会话共享逻辑运行器的 Run 并发容量，并为满载等待、取消和名额交接提供可观察、可验证的行为。

## Requirements

### Requirement: 共享 Run 容量

宿主 MUST 为已启用调度的逻辑运行器配置活跃上限、等待上限及最长排队时间。本地调度器 MUST 对该装配内所有客户端和会话统一裁决。已获名额且在受理中的 Run 与已受理且仍在推进的 Run 均计入活跃数。

#### Scenario: 两个客户端争用一个名额

- **WHEN** 同一装配的两个客户端分别打开甲和乙，活跃上限为 1，甲已占用名额
- **THEN** 乙在队列有空间时进入等待，甲和乙的合计占用最多为 1
- **AND** 乙在等待期间未生成会话持久预约、Run 检查点、Run 执行事件或模型与工具派发

### Requirement: 有界 FIFO 等待

调度器 MUST 按有效请求的入队顺序授予名额。等待上限只计排队项，为零时满载直接拒绝。队列满时 MUST 返回可识别的队列满错误。同会话只允许一个逻辑 Run 处于排队、受理或待提交状态。重试相同 `RunID` 与请求 MUST 共用原排队项；同 ID 异参 MUST 返回冲突。

#### Scenario: 先到先服务与排满

- **WHEN** 甲占用唯一名额，乙先入队，丙随后申请
- **THEN** 等待上限为 1 时丙立即收到队列满错误。等待上限为 2 时丙排在乙之后
- **AND** 释放名额时先推进乙。释放期间的新请求无法越过已有有效等待者

#### Scenario: 重复与冲突提交

- **WHEN** 乙已入队，同会话再次提交原请求、同 ID 异参请求或不同 ID 的请求
- **THEN** 原请求没有新增排队项或延长原期限，同 ID 异参返回冲突，不同 ID 返回会话忙

### Requirement: 取消与等待期限

调度器 MUST 以首次启动调用的上下文与宿主排队期限中先到者控制等待。等待中取消或到期 MUST 移除请求并返回可区分的原因。观察同一请求的重试者可停止自己的等待。取消与授予名额 MUST 按同一顺序裁决。

#### Scenario: 乙等待时取消或超时

- **WHEN** 甲仍占用名额，乙的首次启动调用取消，或队列等待期限先到
- **THEN** 乙的队列位置释放，甲继续运行。乙的历史版本保持不变，检查点与派发数为零
- **AND** 甲后来释放名额时，已取消或到期的请求保持移除状态

#### Scenario: 取消与授予名额竞争

- **WHEN** 等待取消与甲释放名额同时发生
- **THEN** 若取消先裁决，乙尚未进入受理，派发数为零。若已授予，则按原 `Start` 受理边界判定是否启动
- **AND** 明确未受理时归还名额。已受理时，同一 `RunID` 进入既有 `Run.Cancel` 生命周期

### Requirement: 名额释放与交接

调度器 MUST 在运行器确认 Run 终止推进或明确未受理后释放名额一次，并原子选取下一条有效等待请求。受理未知时 MUST 保留原占用并核对原 `RunID`，直到运行器能确认停止推进或未受理。

#### Scenario: 甲终止，乙自动推进

- **WHEN** 甲结束且乙仍等待，即使甲的终态尚未写入会话历史
- **THEN** 乙自动获得名额并按自己的历史启动。甲的会话仍按现有规则等待提交
- **AND** 关闭观察、`Wait` 超时或仅发出运行中取消，都不提前释放甲的名额

#### Scenario: 失败与重复结束信号

- **WHEN** 某次受理明确失败，或活跃 Run 给出可信的成功、失败或取消终态
- **THEN** 原占用恰好释放一次。重复终态信号、重复读取结果和历史提交不增加可用名额
- **AND** 可信终态携带 `CleanupPending` 时同样释放 Run 名额，执行环境继续按自身资源上限清理

#### Scenario: 受理结果不明

- **WHEN** 甲持有唯一名额且受理响应不明，乙已在等待
- **THEN** 甲继续占用，核对期间乙的派发数为零
- **AND** 确认甲已停止推进或未受理后，只释放一次，仍有效的乙自动继续

### Requirement: 调度与 Run 恢复

受管逻辑运行器的启动及可重新派发的恢复 MUST 经同一调度门禁。已占有名额的原 Run MUST 复用原占用。纯读取可信终态与发布会话历史 MUST 可在活跃名额用尽时完成。等待队列仅在当前装配进程内有效。

#### Scenario: 恢复与历史提交

- **WHEN** 活跃名额已满，宿主读取终态或提交已封存增量，或尝试让另一个 Run 从检查点继续执行
- **THEN** 读取和发布可立即继续，可派发的恢复遵守相同容量和队列顺序
- **AND** 受管运行器收到绕过会话调度的可派发调用时，返回可识别的受理错误，派发计数为零

#### Scenario: 进程重启

- **WHEN** 宿主进程退出，乙仍纯排队，甲已有可恢复检查点
- **THEN** 新进程从空等待队列启动。乙只有显式重送才可再次排队，甲沿原 `RunID` 经过调度后按阶段 B/C 的契约恢复
