# session-history Specification

## Purpose

让同一宿主的 Go SDK 在进程重启后读回已提交的会话历史，按原 RunID 续接或核对提交，并让不同会话各自启动、流式观察、取消和推进。

## Requirements

### Requirement: 持久会话与历史快照

会话 MUST 按可信主体和会话标识隔离，并固定逻辑运行器。空会话版本为零。启动 Run MUST 从当前已提交版本取得有界历史窗口，按原顺序选取完整的 Run 消息增量，并将本次输入单独交给运行器。会话 MUST 持久保留已提交历史。

#### Scenario: 跨进程读回并继续对话

- **WHEN** 宿主提交首个 Run，然后在同一宿主启动新进程并为原会话发起下一次 Run
- **THEN** 新进程读到原提交版本与原顺序的历史，模型收到所选历史和本次输入各一次
- **AND** 其他主体通过相同会话标识只能访问自己的会话

#### Scenario: 历史窗口达到上限

- **WHEN** 全部历史超出启动窗口，最近一轮能完整放入
- **THEN** 本次 Run 获得满足限额的最长连续尾部，历史存储保持完整
- **AND** 最近一轮本身超出窗口时，启动返回可识别的限额错误，模型和工具派发均为零

#### Scenario: 会话达到持久容量

- **WHEN** 会话的已提交 Run 数到达配置上限
- **THEN** 新 Run 在受理前返回可识别的容量错误，已有历史和去重回执仍可读取

### Requirement: Run 受理与会话归属

会话 MUST 在可恢复 Run 派发前持久固定原 `RunID`、起始版本及请求。每个会话同时最多持有一个待提交 Run。恢复 MUST 核实原会话、主体、运行器和请求，只续接原 Run；只有能确认原请求尚未受理时才可用相同标识和固定请求发起受理。

#### Scenario: 同一会话仍有待提交 Run

- **WHEN** 宿主给同一会话发一个不同 `RunID` 的请求，原 Run 尚未提交
- **THEN** 返回明确的会话忙，第二次请求的模型和工具派发均为零
- **AND** 原 Run 已终止但会话尚未提交时仍报告会话忙

#### Scenario: 受理响应丢失或原记录不可确认

- **WHEN** 会话已记录启动请求，随后宿主退出或丢失受理响应
- **THEN** 重开会话可找到原 `RunID`。有可信受理记录时恢复该 Run，原已派发工具按阶段 B 核对
- **AND** 只有原权威存储能确认尚未受理时，才允许用固定的同一请求完成受理
- **AND** 若原记录损坏、过期或存储来源无法确认，返回可识别的结果不可用，保留待提交状态和原历史版本

#### Scenario: 受理明确被拒

- **WHEN** 阶段 B 确认本次 `Start` 未受理
- **THEN** 会话释放该 Run 的待提交位置，历史版本、消息和提交回执均保持原样

### Requirement: 按 RunID 原子提交终态

会话 MUST 只追加原 Run 经 `Wait` 确认的 `Result.Messages`，并在一次提交中校验起始版本、登记 `RunID` 回执、推进版本和释放待提交位置。同一结果重试 MUST 返回原回执和原提交版本；归属、结果或起始版本冲突 MUST 保持已提交历史完整。

#### Scenario: 重复提交与响应丢失

- **WHEN** 多个调用方提交同一 `RunID`，或首个提交的响应在持久化后丢失
- **THEN** 该 Run 的消息只追加一次，会话版本只递增一次，各次成功均返回同一回执
- **AND** 即使会话已提交后续 Run、阶段 B 原终态已过期，按原 `RunID` 重试仍返回原提交版本

#### Scenario: 提交来源或版本冲突

- **WHEN** 请求跨会话提交、尝试为相同 `RunID` 发布不同的终态增量，或新的提交携带过时的起始版本
- **THEN** 返回可区分的归属、内容或版本冲突，已提交历史、版本和回执均保持原样

#### Scenario: 非成功终态与观察中断

- **WHEN** 原 Run 以取消、失败或 `ToolOutcomeUnknown` 终止且 `Wait` 给出有效终态
- **THEN** 会话追加本次输入与此前已提交的完整轮次，展示增量、缺配对的工具轮次和重复的 `Answer` 单独入库次数为零
- **AND** 单独的观察断连、`Wait` 超时或取消请求返回均保持待提交状态及原历史版本

#### Scenario: 写入中途进程退出

- **WHEN** 原终态增量已持久保存，会话提交尚未生效时宿主进程退出
- **THEN** 新进程先读到完整旧版本，再以原 `RunID` 和已保存的可信增量完成一次提交
- **AND** 会话提交已生效后退出时，新进程读到完整新版本并可重取原回执

### Requirement: 会话独立推进

共享宿主、可信主体和逻辑运行器的不同会话 MUST 独立推进。在共享依赖仍有容量时，等待、观察、取消及提交某一会话的 Run MUST 限定在该会话和 Run 的范围内。

#### Scenario: 慢工具期间另一会话继续输出

- **WHEN** 会话甲卡在受控慢工具，会话乙启动、收到流式输出并提交
- **THEN** 乙在甲仍阻塞时完成首个 Run，并可用乙自己的新历史启动后续 Run
- **AND** 在乙后续 Run 已开始输出时取消甲，乙继续流式输出并完成提交，双方的事件、消息、工具结果和版本均归属原会话

### Requirement: 只读判定待处理 Run

SDK MUST 按可信主体、会话、原逻辑运行器和 `RunID` 核对持久预约与恢复记录，区分无待处理、待保存、可继续、确认未受理和待核对。判定 MUST 保持会话版本与历史不变，模型和工具派发均为零。

#### Scenario: 预约与已受理检查点

- **WHEN** 两个会话分别持有仅预约的记录和匹配原身份、绑定及请求摘要的未完成检查点
- **THEN** SDK 仅在可信原存储确认未尝试受理且无检查点时返回确认未受理，有匹配检查点时返回原 `RunID` 可继续

#### Scenario: 证据不足

- **WHEN** 有已尝试受理标记但检查点缺失，或原记录损坏、绑定无法验证、终态已过期且没有可信封存增量
- **THEN** SDK 返回待核对并保留原预约，派发与清理预约的次数均为零

### Requirement: 按原 Run 受限处理恢复

恢复动作 MUST 在原会话和 `RunID` 下重新核对当前证据。保存动作只发布可信终态或封存增量。继续动作只接续已受理的检查点并通过现有调度和所有权门禁。清理动作只释放已证明未受理的原预约。所有动作 MUST 沿用既有会话版本与去重规则。

#### Scenario: 原终态待补存

- **WHEN** 原封存增量或可信终态仍可用，或该 `RunID` 已经发布
- **THEN** 补存只发布一次，重试返回原回执。已有可信封存增量时，原 Run 终态过期仍可补存
- **AND** 纯补存无模型或工具派发，也不占用活跃名额

#### Scenario: 等待继续期间证据改变

- **WHEN** SDK 判定原 Run 可继续，但在取得名额前原记录已终止、失去可信性或仍由旧进程持有推进权
- **THEN** 重新核对后返回可信终态、待核对或占用结果。相应操作均无新派发

#### Scenario: 清理未受理预约

- **WHEN** 宿主请求清理已证明未受理的原预约
- **THEN** SDK 仅在持锁复核身份、原存储及未受理证据仍匹配时清理，原输入可交给宿主作为未发送草稿
- **AND** 复核发现受理或证据变化时保留预约，并返回最新判定
